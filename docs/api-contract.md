## 1. Purpose and scope

The backend stores uploaded videos and manages analyses. The **AI service** does the actual computer-vision
work: it reads a video, finds the athlete's pose in every frame, measures the technique and returns
a structured JSON result.

The AI service:

- is a **separate program** in its own repository (`octarsport-ai`) and its own Docker container;
- is **stateless**: it stores nothing between requests and has no database;
- is called **only by the backend**, never by the browser;
- does not know about users, analysis statuses or the web client.

Out of scope for the MVP: GPU processing, streaming results while a video is processed,
authentication between the services, multi-person tracking.

## 2. Environments and general conventions

### 2.1 Addresses

| Environment | AI service base URL (as seen by the backend) |
|---|---|
| Docker Compose | `http://ai:8000` |
| Local dev (AI run directly on the host) | `http://localhost:8000` |

- The backend reads the address from configuration: `Ai__BaseUrl`. It is never hardcoded.
- The AI service listens on `0.0.0.0:8000` inside the container.
- In production the AI service port is **not published** to the outside, it is reachable only inside
  the Docker network.
- Interactive docs generated by FastAPI: `GET /docs` (Swagger UI) and `GET /openapi.json`.

### 2.2 Format rules

- Requests and responses are **JSON, UTF-8**.
- Field names are **`snake_case`**.
- `analysis_id` is a **UUID string** created by the backend. The AI service just echoes it back.
- Durations are in **seconds** (`*_sec`), floating point.
- Coordinates are **normalized floats** (section 5.3).
- Fields that may be absent are always present with `null`, never omitted.
- Unknown fields must be **ignored** by the receiving side (for example, the backend ignores new
  fields in the AI response).
- Rounding: coordinates are rounded to **4 decimal places**, angles and metric values to **1 decimal place**,
  timestamps to **3 decimal places**. This keeps the JSON smaller.

### 2.3 Headers

| Header | Direction | Description |
|---|---|---|
| `Content-Type: application/json` | request, response | Always JSON |
| `X-Request-Id` | request | Set by the backend (value: the `analysis_id`). The AI service writes it to every log line and returns it in the response |
| `X-Request-Id` | response | Same value as in the request |
| `Retry-After` | response | Set on `429` and `503`, seconds to wait |

### 2.4 Authentication

None in the MVP. The AI service is reachable only inside the private Docker network, which is the
protection. If the AI service is ever exposed, a shared secret header (`X-Api-Key`) will be added.

## 3. Domain concepts and responsibilities

### 3.1 Who owns what

| Responsibility | Backend (Adrian) | AI service (Artur) |
|---|---|---|
| Accept and validate the upload (type, size) | yes | no |
| Store the video file | yes | read-only access |
| Analysis id, status, queue, retries | yes | no |
| Decode the video, detect the pose | no | yes |
| Joint angles, metrics, technique errors, score, recommendations | no | yes |
| Catalog of supported sports and movements | publishes it to the frontend | **owns it** (via `/capabilities`) |
| Save results in PostgreSQL | yes | no |
| Split the result into `results` and `landmarks` for the frontend | yes | no |
| Error catalog (`code` values of technique errors) | passes them through | **owns it** |

Important: the AI service **does not invent** scores or errors. Everything that is not implemented
yet stays `null` or an empty array (section 5.1).

### 3.2 Data flow

```
 Frontend ──POST /api/analyses──► Backend ──saves file to /data/uploads/<id>.mp4
                                     │
                                     │  (background worker)
                                     ▼
                         POST http://ai:8000/analyze   {analysis_id, video_path, sport, movement}
                                     │
                                     ▼
                              AI service reads the file, analyses it
                                     │
                                     ▼
                           200 OK + full result JSON
                                     │
                                     ▼
              Backend validates it, stores it in PostgreSQL, sets status = completed
```

### 3.3 Shared storage

The backend and the AI service mount the **same Docker volume** at the **same path** `/data/uploads`.
The backend mounts it read-write, the AI service mounts it **read-only**.

- The AI service must **never write, rename or delete** files in `/data/uploads`.
- For temporary files it uses its own `/tmp`.
- Files are named by the backend: `/data/uploads/<analysis_id>.<ext>`.
- The AI service must only accept `video_path` values that start with `/data/uploads/` and contain no
  `..` segments (protection against path traversal). Symlinks must not be followed outside that folder.

### 4.1 `GET /health` [MVP]

Used by Docker healthchecks. Must respond quickly and must not do heavy work.

`200 OK`
```json
{ "status": "ok" }
```

---

### 4.2 `GET /ready` [MVP]

Returns `200` only when the service can actually analyse a video (MediaPipe model is loaded,
temp folder is writable). The backend waits for it at startup.

`200 OK`
```json
{ "status": "ready" }
```

`503 Service Unavailable` while loading:
```json
{ "status": "loading" }
```

---

### 4.3 `GET /capabilities` [MVP]

Describes what the AI service can analyse. The backend uses it to build the catalog it exposes to the
frontend as `GET /api/sports`, and to validate `sport` and `movement` **before** creating an analysis.
This way a new sport is added in one place (the AI service) and appears in the UI without changing
the backend.

`200 OK`
```json
{
  "service": "octarsport-ai",
  "service_version": "0.1.0",
  "schema_version": "1.0",
  "algorithm_version": "0.1.0",
  "limits": {
    "max_duration_sec": 60,
    "min_duration_sec": 1,
    "max_width": 3840,
    "max_height": 3840
  },
  "sports": [
    {
      "code": "volleyball",
      "name": "Volleyball",
      "movements": [
        { "code": "serve", "name": "Serve", "implemented": false },
        { "code": "spike", "name": "Spike", "implemented": false },
        { "code": "jump", "name": "Jump", "implemented": false }
      ]
    }
  ]
}
```

- `implemented` is `false` while only raw pose landmarks are returned and no technique analysis exists
  for that movement yet. The backend may hide movements that are not implemented, or show them with a
  note. [Draft]
- `schema_version` is the version of the **result format** (section 5). The backend checks it matches
  what it supports.

---

### 4.4 `POST /analyze` [MVP]

Analyses one video and returns the full result. The request is **synchronous**: the connection stays
open until the analysis is done. The backend calls it from a background worker with a long timeout
(section 8.2), never from an HTTP request of the browser.

**Request**
```json
{
  "analysis_id": "3f2a9c1e-7b4d-4c3a-9a51-2f6d8e0b1c77",
  "video_path": "/data/uploads/3f2a9c1e-7b4d-4c3a-9a51-2f6d8e0b1c77.mp4",
  "sport": "volleyball",
  "movement": "spike",
  "options": null
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `analysis_id` | string (UUID) | yes | Echoed in the response and logs |
| `video_path` | string | yes | Absolute path inside the shared volume (section 3.3) |
| `sport` | string | yes | Code from `/capabilities` |
| `movement` | string | yes | Code from `/capabilities` |
| `options` | object or null | no | Tuning parameters, see below. `null` means defaults |

**`options` [Draft]**: all fields optional, defaults are chosen by the AI service.
```json
{
  "model_complexity": 1,
  "min_detection_confidence": 0.5,
  "min_tracking_confidence": 0.5,
  "smoothing": false
}
```
The backend does not send `options` in the MVP. They exist so Artur can experiment from tests without
changing the contract.

**Response: `200 OK`**

The full result, described in section 5.1. Example (shortened, `frames` contains one entry per frame):
```json
{
  "schema_version": "1.0",
  "analysis_id": "3f2a9c1e-7b4d-4c3a-9a51-2f6d8e0b1c77",
  "status": "completed",
  "sport": "volleyball",
  "movement": "spike",
  "video": { "fps": 30.0, "duration_sec": 5.0, "frame_count": 150, "width": 1080, "height": 1920 },
  "detection": { "frames_with_pose": 146, "detection_rate": 0.9733 },
  "overall_score": null,
  "score_breakdown": [],
  "metrics": [],
  "errors": [],
  "recommendations": [],
  "frames": [
    {
      "frame_index": 0,
      "timestamp_sec": 0.0,
      "pose_detected": true,
      "landmarks": {
        "nose": { "x": 0.52, "y": 0.18, "z": -0.31, "visibility": 0.99 }
      },
      "angles": null
    }
  ],
  "processing": {
    "duration_sec": 12.4,
    "algorithm_version": "0.1.0",
    "model": { "name": "mediapipe_pose", "version": "0.10.21", "complexity": 1 },
    "smoothing": "none"
  }
}
```
(A real frame contains all 33 landmarks.)

**Errors:** see section 6. Typical: `400 invalid_request`, `404 video_not_found`,
`422 video_unreadable`, `422 no_person_detected`, `429 busy`.

**Behavior rules**

- The service analyses **every frame** of the video in order and returns exactly one entry per frame.
  [Draft, see open question 4]
- The result must be **deterministic**: the same video and options give the same output.
  This makes retries safe (`/analyze` is idempotent).
- The service must not modify or delete the video.
- If the AI service is busy, it replies `429 busy` immediately instead of queueing silently.
- All the work for one request should end within `max_processing_sec`; otherwise it aborts and returns
  `504 processing_timeout`. Suggested default: 600 seconds. [Draft]

---

### 4.5 `POST /jobs` and `GET /jobs/{analysis_id}` [Planned]

An asynchronous mode for very long videos or heavier algorithms:
`POST /jobs` (same body as `/analyze`) returns `202 Accepted` immediately, `GET /jobs/{analysis_id}`
returns `{ "status": "processing" | "completed" | "failed", "progress": 0..100, "result": {...} | null,
"error": {...} | null }`. When this exists, the backend gets **real progress** to show in the UI.
Not needed for the MVP.

## 5. Data schemas

### 5.1 Result (`POST /analyze` response)

```json
{
  "schema_version": "1.0",
  "analysis_id": "…",
  "status": "completed",
  "sport": "volleyball",
  "movement": "spike",
  "video": { "fps": 30.0, "duration_sec": 5.0, "frame_count": 150, "width": 1080, "height": 1920 },
  "detection": { "frames_with_pose": 146, "detection_rate": 0.9733 },
  "overall_score": null,
  "score_breakdown": [],
  "metrics": [],
  "errors": [],
  "recommendations": [],
  "frames": [ /* see 5.2 */ ],
  "processing": { /* see below */ }
}
```

| Field | Type | Description |
|---|---|---|
| `schema_version` | string | `"1.0"` |
| `analysis_id` | string | Echo of the request |
| `status` | string | Always `"completed"` in a `200` response. Failures are returned as errors (section 6), not as a result with another status |
| `sport`, `movement` | string | Echo of the request |
| `video.fps` | number | Frames per second of the video |
| `video.duration_sec` | number | Video duration |
| `video.frame_count` | integer | Number of frames the service processed. **Must equal `frames.length`** |
| `video.width`, `video.height` | integer | **Displayed** size in pixels, after the rotation metadata is applied |
| `detection.frames_with_pose` | integer | Frames where `pose_detected` is `true` |
| `detection.detection_rate` | number | `frames_with_pose / frame_count`, 0 to 1 |
| `overall_score` | number or null | 0 to 100, or `null` if scoring is not implemented |
| `score_breakdown` | array | Details of the score; empty while there is no score |
| `metrics` | array | Measured values; empty until implemented |
| `errors` | array | Technique errors found; empty until implemented |
| `recommendations` | array | General advice; empty until implemented |
| `frames` | array | Per-frame skeleton data (5.2) |
| `processing` | object | Technical information about this run, for debugging. Not shown to users |

**Until the scoring algorithm exists: `overall_score` is `null` and `score_breakdown`, `metrics`,
`errors`, `recommendations` are `[]`. Do not invent scores or errors.**

**`score_breakdown[]`**
```json
{ "criterion": "arm_swing", "label": "Arm swing", "score": 72.5, "weight": 0.3 }
```
`score` is 0 to 100. If `overall_score` is not `null`, the weights should sum to 1 (tolerance 0.001)
and `overall_score` should equal the weighted sum. The backend does not recompute it.

**`metrics[]`**
```json
{
  "code": "right_elbow_angle_at_contact",
  "label": "Right elbow angle at contact",
  "value": 168.4,
  "unit": "deg",
  "frame_index": 87
}
```
`unit` is one of `deg`, `sec`, `m`, `m_s`, `ratio`. `frame_index` may be `null`. Metrics in meters
require camera calibration and are not expected in the first versions.

**`errors[]`** (technique errors)
```json
{
  "code": "elbow_too_low",
  "title": "Elbow drops too low",
  "description": "The hitting elbow is below shoulder level during the swing.",
  "severity": "warning",
  "phase": "swing",
  "start_frame": 62,
  "end_frame": 78,
  "start_time_sec": 2.067,
  "end_time_sec": 2.6,
  "joints": ["right_elbow", "right_shoulder"],
  "recommendation": "Keep the elbow high and in line with the shoulder."
}
```

- `code`: **stable** `snake_case` identifier. Once released it is never renamed or reused for another
  meaning, because the frontend uses it for translations. Artur maintains the full list in
  `octarsport-ai/docs/errors-catalog.md`.
- `severity`: `info`, `warning` or `critical`.
- `phase`, `start_frame`, `end_frame`, `start_time_sec`, `end_time_sec`, `recommendation` may be `null`;
  `joints` may be `[]`. Joint names come from the 33 landmark names (section 5.3).
- `start_frame` and `end_frame` are inclusive indexes into `frames`.
- `title`, `description`, `recommendation` are English default texts.

**`recommendations[]`** (general advice)
```json
{ "code": "improve_approach_speed", "text": "Work on a faster last two steps of the approach.", "priority": 1 }
```
`priority`: 1 is the most important.

**`processing`**
```json
{
  "duration_sec": 12.4,
  "algorithm_version": "0.1.0",
  "model": { "name": "mediapipe_pose", "version": "0.10.21", "complexity": 1 },
  "smoothing": "none"
}
```
`duration_sec` is the wall-clock time of the analysis. `smoothing` is `none` or the name of the filter
used. This object helps to debug and compare algorithm versions, the frontend does not use it.

---

### 5.2 `frames[]`

```json
{
  "frame_index": 0,
  "timestamp_sec": 0.0,
  "pose_detected": true,
  "landmarks": {
    "nose": { "x": 0.52, "y": 0.18, "z": -0.31, "visibility": 0.99 },
    "right_elbow": { "x": 0.31, "y": 0.30, "z": -0.15, "visibility": 0.98 }
  },
  "angles": null
}
```

Rules:

- `frames.length === video.frame_count`, ordered by `frame_index`, starting at `0`, **no gaps**.
- `timestamp_sec = frame_index / video.fps`. [Draft, see open question 3 about variable frame rate]
- If no person is found in a frame: `pose_detected` is `false`, `landmarks` is `null`, `angles` is `null`.
  The frame still appears in the array.
- When `pose_detected` is `true`, `landmarks` contains **all 33 points** (section 5.3).
- `angles` is `null` until joint angles are implemented. After that, either `null` (no pose) or an
  object, see section 9.4.

---

### 5.3 Landmarks and coordinates

Based on **MediaPipe Pose** (33 points). The AI service converts MediaPipe output into this format.

- `x`, `y`: normalized to **0..1** relative to the **displayed** video frame:
  `x = 0` left edge, `x = 1` right edge, `y = 0` top, `y = 1` bottom. Values slightly outside 0..1 are
  allowed when a body part leaves the frame.
- `z`: relative depth, smaller means closer to the camera, on roughly the same scale as `x`.
- `visibility`: 0..1, the confidence that the point is visible.
- `left` and `right` are the **athlete's** left and right, not the viewer's (same as MediaPipe).
- The frame is the **displayed** orientation. If the phone video has rotation metadata, the AI service
  applies it before detection, so that coordinates and `video.width`/`video.height` match what a browser
  shows. Artur must verify this on a real portrait phone video.

**The 33 landmark names (index order, same as MediaPipe)**

| # | name | # | name | # | name |
|---|---|---|---|---|---|
| 0 | `nose` | 11 | `left_shoulder` | 22 | `right_thumb` |
| 1 | `left_eye_inner` | 12 | `right_shoulder` | 23 | `left_hip` |
| 2 | `left_eye` | 13 | `left_elbow` | 24 | `right_hip` |
| 3 | `left_eye_outer` | 14 | `right_elbow` | 25 | `left_knee` |
| 4 | `right_eye_inner` | 15 | `left_wrist` | 26 | `right_knee` |
| 5 | `right_eye` | 16 | `right_wrist` | 27 | `left_ankle` |
| 6 | `right_eye_outer` | 17 | `left_pinky` | 28 | `right_ankle` |
| 7 | `left_ear` | 18 | `right_pinky` | 29 | `left_heel` |
| 8 | `right_ear` | 19 | `left_index` | 30 | `right_heel` |
| 9 | `mouth_left` | 20 | `right_index` | 31 | `left_foot_index` |
| 10 | `mouth_right` | 21 | `left_thumb` | 32 | `right_foot_index` |

## 6. Errors

### 6.1 Error response format

Every non-2xx response from the AI service has this body:

```json
{
  "error": {
    "code": "video_unreadable",
    "message": "Cannot open video file.",
    "details": null
  }
}
```

- `code`: stable `snake_case` string. The backend branches on `code`, never on `message`.
- `message`: English text for logs.
- `details`: optional object with extra data (for example the failing field), otherwise `null`.

FastAPI's default validation error format (`{"detail": [...]}`) must be replaced by this format
(custom exception handlers), so that the backend parses only one shape.

### 6.2 Error catalog

| HTTP | `code` | When | Retry by backend? |
|---|---|---|---|
| 400 | `invalid_request` | Body is malformed or a field is missing or has the wrong type | no |
| 400 | `invalid_video_path` | `video_path` is outside `/data/uploads/` or contains `..` | no |
| 404 | `video_not_found` | File does not exist | no |
| 422 | `unsupported_sport` | `sport` is not in `/capabilities` | no |
| 422 | `unsupported_movement` | `movement` is not supported for this sport | no |
| 422 | `video_unreadable` | File exists but cannot be decoded as a video | no |
| 422 | `video_too_long` | Duration is above `limits.max_duration_sec` | no |
| 422 | `video_too_short` | Duration is below `limits.min_duration_sec` | no |
| 422 | `no_person_detected` | **No frame** has a detected person (`frames_with_pose = 0`) | no |
| 429 | `busy` | The service is processing the maximum number of videos, see `Retry-After` | yes, with delay |
| 503 | `not_ready` | Models are still loading | yes, with delay |
| 504 | `processing_timeout` | The analysis exceeded `max_processing_sec` | no |
| 500 | `internal_error` | Unexpected failure | once |

Note on `no_person_detected`: it is returned **only** when there is not a single frame with a person.
If a person is found in some frames, the request succeeds and the low quality is reflected by
`detection.detection_rate`.

### 6.3 Mapping to the frontend error codes

The backend translates AI errors into the `error.code` that the frontend sees in a `failed`
analysis (see the Frontend ↔ Backend contract, section 6.3):

| AI service result | Backend sets `error.code` |
|---|---|
| `video_unreadable`, `video_too_long`, `video_too_short` | `ai_video_unreadable` |
| `no_person_detected` | `ai_no_person_detected` |
| `processing_timeout`, or the backend's own request timeout | `ai_timeout` |
| `busy` / `not_ready` still failing after all retries, connection refused, DNS failure | `ai_unavailable` |
| `invalid_request`, `invalid_video_path`, `video_not_found`, `unsupported_sport`, `unsupported_movement`, `internal_error`, an invalid response | `internal_error` |

`invalid_request`, `invalid_video_path`, `video_not_found` and `unsupported_*` mean a bug on the
backend side (it should have prevented them), so they are logged with the full AI error.

## 7. Limits and validation [Draft]

| Rule | Value | Enforced by |
|---|---|---|
| Allowed containers | `.mp4`, `.mov` | Backend (upload) |
| Max file size | 200 MB | Backend (upload) |
| Max duration | 60 s | Backend (after probing) and AI service |
| Min duration | 1 s | Backend and AI service |
| Max resolution | 3840 × 3840 | AI service |
| Max parallel analyses in the AI service | 1 (configurable `AI_MAX_CONCURRENCY`) | AI service |
| `max_processing_sec` | 600 | AI service |
| People in video | One athlete. If several are visible, the AI tracks the most prominent person | AI service |
| Result size | Up to about 10 MB of JSON for a 60 s video | both |

Because the AI service allows only a limited number of parallel analyses, the backend worker uses
the **same concurrency** (`Ai__MaxConcurrency`, default 1). Extra uploads wait in the backend queue
with status `queued`.

## 8. Backend integration guide (Adrian)

### 8.1 Client structure

An interface hides the AI service so that it can be faked and tested:

```csharp
public interface IAiAnalyzerClient
{
    Task<AiCapabilities> GetCapabilitiesAsync(CancellationToken ct);
    Task<AiAnalysisResult> AnalyzeAsync(AiAnalysisRequest request, CancellationToken ct);
}
```

- `HttpAiAnalyzerClient` calls the real service through `HttpClient` (registered with `AddHttpClient`).
- `FakeAiAnalyzerClient` returns a prepared result and is enabled by `Ai__UseFake=true`.

### 8.2 Timeouts and retries

| Setting | Value [Draft] |
|---|---|
| Connect timeout | 5 s |
| Request timeout for `/analyze` | 10 minutes (must be above the AI's `max_processing_sec`) |
| Request timeout for `/health`, `/ready`, `/capabilities` | 5 s |
| Retries on `429`, `503` and connection errors | up to 3, delays 2 s, 5 s, 15 s (respect `Retry-After`) |
| Retries on `500` | 1 |
| Retries on any `4xx` except `429` | none |

`/analyze` is idempotent (section 4.4), so retrying is safe.

### 8.3 Validating the AI response

Before saving, the backend checks the result and, if a check fails, marks the analysis `failed`
with `internal_error` and logs the details:

- `schema_version` has the same **major** version as the backend supports;
- `analysis_id`, `sport`, `movement` match the request;
- `video.frame_count == frames.length`, and `frames[i].frame_index == i`;
- `frames_with_pose` equals the number of frames with `pose_detected = true`;
- `pose_detected = true` implies 33 landmarks; `pose_detected = false` implies `landmarks = null`;
- `overall_score` is `null` or in 0..100; every `severity` is a known value;
- the JSON is not larger than the configured maximum.

### 8.4 What the backend stores and serves

| Data | Storage | Served to the frontend as |
|---|---|---|
| `video`, `detection`, `overall_score`, `score_breakdown`, `metrics`, `errors`, `recommendations` | PostgreSQL `jsonb` column | `GET /api/analyses/{id}/results` |
| `frames` | PostgreSQL `jsonb` column (or a file, to be decided by the backend) | `GET /api/analyses/{id}/landmarks` |
| `processing` | PostgreSQL `jsonb` column | not exposed |

### 8.5 Startup and health

The backend checks `GET /ready` before starting to process the queue and treats a failing AI service as
temporary: analyses stay `queued`, they do not fail. It also calls `GET /capabilities` on start (and
periodically) to build `GET /api/sports`.

### 8.6 Logging

The backend sends `X-Request-Id: <analysis_id>` on every call and logs the AI response status and
`processing.duration_sec`. Artur's logs contain the same id, so one analysis can be traced across both services.

### 9.2 Pydantic models

```python
from typing import Literal
from pydantic import BaseModel

class Landmark(BaseModel):
    x: float
    y: float
    z: float
    visibility: float

class Frame(BaseModel):
    frame_index: int
    timestamp_sec: float
    pose_detected: bool
    landmarks: dict[str, Landmark] | None
    angles: dict[str, float] | None = None

class VideoInfo(BaseModel):
    fps: float
    duration_sec: float
    frame_count: int
    width: int
    height: int

class Detection(BaseModel):
    frames_with_pose: int
    detection_rate: float

class ScoreItem(BaseModel):
    criterion: str
    label: str
    score: float
    weight: float

class Metric(BaseModel):
    code: str
    label: str
    value: float
    unit: Literal["deg", "sec", "m", "m_s", "ratio"]
    frame_index: int | None = None

class TechniqueError(BaseModel):
    code: str
    title: str
    description: str
    severity: Literal["info", "warning", "critical"]
    phase: str | None = None
    start_frame: int | None = None
    end_frame: int | None = None
    start_time_sec: float | None = None
    end_time_sec: float | None = None
    joints: list[str] = []
    recommendation: str | None = None

class Recommendation(BaseModel):
    code: str
    text: str
    priority: int

class ModelInfo(BaseModel):
    name: str
    version: str
    complexity: int

class Processing(BaseModel):
    duration_sec: float
    algorithm_version: str
    model: ModelInfo
    smoothing: str

class AnalyzeRequest(BaseModel):
    analysis_id: str
    video_path: str
    sport: str
    movement: str
    options: dict | None = None

class AnalysisResult(BaseModel):
    schema_version: str = "1.0"
    analysis_id: str
    status: Literal["completed"] = "completed"
    sport: str
    movement: str
    video: VideoInfo
    detection: Detection
    overall_score: float | None = None
    score_breakdown: list[ScoreItem] = []
    metrics: list[Metric] = []
    errors: list[TechniqueError] = []
    recommendations: list[Recommendation] = []
    frames: list[Frame]
    processing: Processing
```

### 9.3 Reading the video

- Prefer `opencv-python-headless` in the container (no GUI libraries needed).
- Get `fps`, frame count, width and height from the file, but trust the **actually decoded frames** for
  `frame_count`.
- Apply the rotation metadata so the frame is in the displayed orientation (check
  `cv2.CAP_PROP_ORIENTATION_AUTO` in your OpenCV version and test with a portrait phone video).
- OpenCV returns BGR, MediaPipe expects **RGB**: convert before detection.
- Release the capture in a `finally` block.
- Reject unreadable, too long or too short videos with the codes from section 6.2 **before** the heavy work.

### 9.4 Joint angles [Planned]

`frames[i].angles` is an object of joint angles in degrees (0 to 180), for example:
```json
{ "right_elbow": 142.5, "left_elbow": 90.1, "right_knee": 171.0 }
```

Proposed angle names: `left_elbow`, `right_elbow`, `left_shoulder`, `right_shoulder`, `left_hip`,
`right_hip`, `left_knee`, `right_knee`, `left_ankle`, `right_ankle`. Definition: the angle at the named joint between the two
adjacent segments (for `right_elbow`: shoulder → elbow → wrist). [Draft]

**Aspect ratio caveat:** `x` and `y` are normalized separately by width and height. Before computing an
angle, convert to pixels (`x * width`, `y * height`), otherwise angles in non-square videos are distorted.
If any of the three points has `visibility` below 0.5, the angle for that frame should be omitted from the object
(or `null`).

### 9.5 Concurrency and performance

- Process one video at a time by default. Limit parallel requests with a semaphore
  (`AI_MAX_CONCURRENCY`, default 1) and answer `429 busy` when it is full.
- Run the heavy analysis in a worker thread or process pool (for example `run_in_threadpool`),
  so the `/health` and `/ready` endpoints stay responsive while a video is processed.
- Create the MediaPipe `Pose` object once per analysis (not per frame), and load models at startup.
- Do not keep results in memory after the response is sent.
- Set a memory limit in Docker and make sure a long video does not load all decoded frames at once:
  process frame by frame and keep only the compact landmark data.

### 9.6 Dockerfile and Compose

Requirements for `octarsport-ai/Dockerfile`:

- base image `python:3.11-slim`;
- install only needed system libraries (OpenCV headless usually needs `libglib2.0-0`);
- `pip install --no-cache-dir -r requirements.txt` with **pinned versions**
  (`opencv-python-headless`, `mediapipe==0.10.21`, `numpy`, `fastapi`, `uvicorn`, `pydantic`);
- run as a **non-root user**;
- start command: `uvicorn app.main:app --host 0.0.0.0 --port 8000`;
- bake the MediaPipe model files into the image so there is no download at startup.

## 11. Versioning and change process

- `schema_version` changes when the **result format** changes incompatibly. The backend refuses a result
  with a different major version and the AI service reports its version in `/capabilities`.
- `algorithm_version` changes when analysis logic changes (new errors, a different score). It does not affect
  compatibility but is stored with each result, so old results can be told apart.
- Backward-compatible changes (new optional fields, new `sport`, `movement`, `phase` or error `code` values)
  do not change the version. Both sides must ignore unknown fields and handle unknown string values gracefully.
- Process: open a Pull Request in `octarsport-general` that edits this file, tag both owners (and Yura if the change
  reaches the frontend contract), merge only after approval.
- The result format here and in section 5 of the Frontend ↔ Backend contract must stay consistent:
  the backend returns exactly what the AI service produced, split into `results` and `landmarks`.

## 12. Open questions

Items to discuss and close between Adrian and Artur:

1. **Sync vs async.** Is a synchronous `/analyze` fine for the MVP (typical video about 5 to 30 seconds of
   processing)? Or should `/jobs` with progress come earlier?
2. **Time budget.** How long does analysis of a 5 s and a 60 s video take on CPU on the machine that will run it?
   This sets `max_processing_sec` and the backend timeout.
3. **Variable frame rate.** Phone videos can have a variable frame rate. Is `timestamp_sec = frame_index / fps` precise
   enough, or should the AI return the real timestamp of each decoded frame? (Wrong timestamps make the skeleton
   drift against the video in the frontend.)
4. **Every frame or sampling.** Can the algorithm process every frame within the time budget? If not, do we
   return every Nth frame (and add `frame_stride` to the contract) or interpolate in between?
5. **Smoothing.** Are raw MediaPipe landmarks returned, or filtered ones? The frontend skeleton looks calmer with
   smoothing, but analysis may prefer raw values. We could return raw and let the frontend smooth.
6. **No person threshold.** Is `no_person_detected` only for zero frames with a pose (current proposal), or should
   a low `detection_rate` (for example below 0.2) also be a failure?
7. **`options`.** Which tuning parameters does Artur really want to expose, if any?
8. **Model complexity.** Which MediaPipe `model_complexity` is the default (speed against accuracy)?
9. **Error catalog ownership.** Artur owns the list of technique error codes. How do we share it with Yura for translations
   (a generated JSON file in `octarsport-general`)?
10. **Large results.** Is a 10 MB JSON over the internal network acceptable, or should the AI write the result to a shared
    volume and return only its path?
11. **Angles.** Which angles and which definitions are needed for volleyball movements, and what is the first movement to implement?
12. **Hardware.** Is CPU enough for the target load? Is GPU something we plan for?
